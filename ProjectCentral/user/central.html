#0 · Why?

The World behind the context

Central aims to fill a gap in agentic work: bringing together the agentic World born in the Human–Agent relationship. An Agent encounters a World through the context it receives. The context of that context is a filesystem. Central gives that filesystem a structure, relating each project’s own Central to common Central ground. Instances of agency on a machine can then be understood as nodes in a field of activity, whose context files and code carry the inputs and outputs of agentic work.

#1 · What?

A minimal CLI for a structured filesystem

Central is a CLI that safely and minimally structures a filesystem. It anchors relationships between projects, creates spaces for human- and Agent-developed artifacts, and provides a recursive home for AI work across the system.

Project the structure; retain the work

Central projects a filesystem structure, laying the infrastructure for Agent navigation and human clarity around work. The conditions that determine an Agent’s World live outside any particular harness session and remain available between its activities. Tending those conditions becomes a quiet starting point for developing one’s own relationship with AI Agents and their work.

#5 · Why-For?

The minimal foundation for an O:I World

Central provides the foundational bootstrap for the O:I paradigm. It is intended as the first install and the only necessary package for beginning to work in that paradigm. A person can keep their existing setup while Central gives it a more integrated, relationally aware structure.

This foundation supports the other O:I packages: it gives AIKit’s wiki functions a source home and receives projections from Workcell machine setups. Its first concern is the initial disclosure of a person’s World to an Agent: making the context being offered clear and worth tending.

Central gives durable principles, governance and user context a common home from which they can inform projects at the depth and scope the user chooses. The user determines how that material propagates and lives. Central gives the ratified basis a home.

The World behind a session

Agentic work begins in a relationship: a person offers an Agent context, intention and the means to act. Before a task can make sense, there is already a World around it—files, projects, practices, machines and the person’s reasons for doing the work.

Central addresses this prior condition. The filesystem holds the context from which a session begins and the artifacts it leaves behind. Giving it a common, recursive structure lets each project relate to durable ground that can be encountered across sessions and harnesses.

The practical gap appears when that relationship has to be reconstructed repeatedly. Personal guidance is copied between repositories. Project intent is stranded in a conversation. An Agent receives a task without the surrounding reasons and constraints. Central gives these materials a place in a connected World, so the initial disclosure to an Agent can be deliberate.

The aim is a foundation a person can tend: what should carry across projects, what belongs to this particular project, and what an Agent should encounter before beginning work. [[central:seed:q0|The overview’s Why]] is the human-authored starting point for this expanded reading.

founding position

Continuity at the scale of a day and a life

A coherent working world needs both enduring intention and room for unfinished thought. Central gives current notes, open questions, useful references and attributed handoffs a shared NOW. A Flow lets one developing thought continue in an editable source over several days. DAY records preserve what happened and what remains live, allowing tomorrow’s work to resume with useful continuity.

Developed ways of working can be kept alongside the projects that use them. A person can maintain reusable Skills, compose Methods, establish common Agent guidance and refine that guidance for a particular project. The same principle extends to the working environment. A person can describe what a workstation or server should provide, inspect what is present, review the changes needed, apply them through available integrations and verify the result. Restoring an environment becomes a deliberate operation with a readable outcome.

Together, these capabilities allow useful practice to accumulate. Authored intention remains available; current work can be resumed; environments can be restored; and returned results have somewhere meaningful to go.

What the experience should preserve

Ownership through ordinary source. A person should be able to inspect the files carrying their preferences, project intent and ongoing thought with familiar tools. Existing useful source can remain in place. Identity and provenance allow the surrounding system to understand that source as it changes.

Proportionate authorship. A small project may need one good note. A mature product may need a substantial account containing vision, stories, design and architecture. The amount of documentation should follow the meaning that needs to be held. Initialisation provides the available structure; authorship gives it substance.

Consequence made legible. A proposed durable change should show the target, reason, relevant context and actual difference. The person can accept, revise or reject it. That review should be concentrated on choices that matter rather than continual supervision of context collection and bookkeeping.

Continuity across interfaces. Finding a project, reading source or planning an environment change should preserve the same meaning when invoked by an Agent, CLI or desktop. Each interface can offer an appropriate experience around the same operation.

The CLI and its functional scope

Central is a CLI for safely and minimally structuring a filesystem into a common home for Human–Agent work. It establishes common Central ground, relates project-level homes to that ground, and provides spaces for human source, Agent artifacts and ongoing work.

The CLI makes that structure inspectable and usable through native operations. A person can establish a root, locate a project, inspect its structure and sources, add missing facilities, and maintain the material through which collaboration continues. The files remain accessible through the person’s existing tools.

This recursive filesystem foundation is the product’s defining function. The capabilities below develop it: source identity makes the ground traceable; NOW and Flow carry ongoing activity; governance and profiles hold reusable relationships; machine operations connect the declared environment to the work. protocol method

Bring an existing project into view

Central begins by projecting the shared filesystem structure. At root scope there is common ground and Work; within a project there is a local home related to that ground. Initialisation establishes the available shape. Inspection shows what exists. Additive reprojection supplies missing pieces while retaining existing work.

These conditions persist outside the activity of any single harness session. An Agent can enter the project, inspect current source, do its work and leave a result in the same continuing World. The user can develop the ground with ordinary file tools between sessions. The amount of structure and context used follows the work.

The journeys below describe how that foundation is inhabited, beginning with an existing project. They expand [[central:seed:q2|the overview’s How]].

Situation. A person asks an Agent to help with a project whose purpose is scattered across existing files and development conversations. They want to begin useful work without first reorganising the repository.

Encounter. The Agent locates the project through Work, inspects its current structure and reads candidate sources. It follows wayfinder refinements and ticket comments where they change earlier scope. It presents a compact account of the need being met, the intended experience and material uncertainties, with the source behind each determination.

The person can recognise useful existing sources in place and choose a consolidated account where that improves clarity. A structural plan can supply missing ProjectCentral facilities. The authored account is composed around what the product means; source relations record its treatment.

Successful result. The next Agent can find the project, recover the recognised purpose and distinguish current implementation from intended outcomes. The person has a readable place to improve the product’s direction. The remaining historical material stays available for review.

Refine intent as development reveals a difference

Situation. An Agent implementing a user journey discovers that the current source supports only part of the intended experience. For example, history and comparison exist, but the proposed desktop recovery flow needs a clear review and apply step.

Encounter. The Agent identifies the affected intent and design unit, inspects the implementation and returns the concrete difference. It explains what a person can currently do, what remains in the intended workflow, and which decision or implementation change would close the gap.

If the intention itself should change, the person reviews a proposed revision with its reason and source basis. An accepted edit uses the current revision. When a concurrent edit has changed that basis, the proposal is reconciled with the newer source before application.

Successful result. Implementation and intention become more closely aligned through an explicit decision. Useful findings strengthen the existing account and capability record. Each subsequent development task can point to the same intended outcome.

The contracts behind a source encounter

Four distinctions support the workflows in this account.

  1. Identity and location. A source or Flow needs a reference that can continue as its content changes. Where supported, renaming and retained-in-place adoption preserve that reference. The actual current location remains disclosed.
  2. Role and standing. A document’s use in a project and the authority of its claims are recorded separately. Generated synthesis remains attributable to its generation until the relevant recognition occurs. A source may contain several kinds of claim.
  3. Revision and mutation. A read provides the basis for a later change. Writes compare that expected revision with current source. The result either identifies the applied change or presents the conflict/proposal requiring reconciliation.
  4. Source and its readings. The human account, implementation, observed results and Agent interpretation retain their own identities. A reader can follow the relationship between them and inspect the underlying source.

Change reconciliation extends this contract to ordinary editors. Central can detect an external edit on the next reconciliation, record a source change and expose it after a consumer’s cursor. When the actor is unknown, attribution stays unknown. Historical comparison uses the available provider; a recovery preview checks the current basis before returning historical content for review.
